# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Naming

The project is named `acoustic_geolocation`, not "MLAT". MLAT (multilateration) normally means locating a *transmitter* via time-difference-of-arrival across multiple spatially-separated receivers. This project does the opposite: a single recording's Doppler curves are matched against known ADS-B flight tracks to locate the *receiver*. If the project is ever renamed again, keep it reflecting single-recording Doppler-curve matching, not multilateration.

## Project status

All four pipeline stages (`physics/`, `audio/`, `adsb/`, `grid/`), `pipeline.py`, and `cli.py` are implemented and tested, including a full end-to-end test (synthetic audio + a local ADS-B CSV dump, through the real CLI/pipeline, recovering the true location to within ~35m and T0 to within ~0.2s on the test fixture). This is v1: real-world accuracy, performance at scale, and the limitations noted throughout this file are all still open. Commands:

- Install (editable, with dev deps): `pip install -e '.[dev]'`
- Run tests: `pytest`
- Run a single test: `pytest tests/test_physics_propagation.py::test_name`
- Geolocate a recording: `acoustic-geolocate locate <audio_file> <YYYY-MM-DD> <lat_min,lon_min,lat_max,lon_max> --adsb <dump.csv> [--dem flat:<elevation_m>] [--output json|text]`
- Inspect detected audio events only (debugging): `acoustic-geolocate events <audio_file>`

## Purpose

The goal is to geolocate a video/audio recording by extracting the Doppler-shifted sound of background aircraft from its spectrogram and matching that acoustic signature against historical ADS-B flight-track data, narrowing down to the exact location the recording was made.

## Architecture (per README.md design)

The pipeline has four conceptual stages, intended to be implemented in this order since each depends on the output of the previous one:

1. **Audio Analysis** — generate a spectrogram from the input recording and extract discrete Doppler "events" (curves), plus the time offset between events and rough speed/distance ranges per event.
2. **ADS-B ingestion** — fetch historical flight data for the date and rough search area; *all* tracks are kept at this stage (filtering to aircraft types whose acoustic signature is modeled, e.g. propeller aircraft, happens later and only for match candidates — see invariants below, non-matching types must stay available for the silence check).
3. **Coarse grid filtering** — over a coarse geospatial grid (~200m), compute the delayed closest-point-of-approach (CPA) per candidate point per event, accounting for sound travel time (not just flight time), and keep only points whose predicted inter-event time offset matches the measured one *and* whose predicted "silence" (no other audible flights between events) matches the recording.
4. **Precision Doppler modeling & scoring** — upscale surviving coarse points to a fine grid (~100m), generate a theoretical Doppler curve per candidate point by integrating emission-time vs. observation-time (sound emitted at `t_emitted` is heard at `t_emitted + distance(t_emitted)/c`, so the model must solve for the aircraft's position *at emission time*, not at heard time), and score the modeled curve against the audio stage's own extracted ridge frequencies (not spectrogram brightness — see invariants below). The highest-scoring point is the answer.

Key invariants to preserve when implementing this:
- **Emission-time vs. heard-time distinction**: all distance/velocity/Doppler calculations for a modeled curve must be evaluated at the aircraft's position at *emission* time, found by solving the implicit delay equation `t_heard = t_emitted + d(t_emitted)/c`, not simply at the position at the observation timestamp. The README's pseudocode line `emission_time = t - distance(position_at(t))/c` is only the *first* fixed-point iteration of that solve, not a converged answer — never copy it verbatim as the final computation.
- **Radial velocity** is the aircraft velocity vector's component along the aircraft→observer unit vector at emission time.
- **The recording's absolute start time (`T0`) is unknown** and must be solved for jointly with location — treat it as a nuisance parameter fit alongside each candidate point, not a given input.
- **Each detected Doppler event's canonical time is the `f = f0` crossing, where radial velocity is zero** — not the event's start, peak, midpoint, or point of steepest slope (those are measurably different instants, not interchangeable) — because the `f = f0` crossing is exactly the instant the delayed-CPA computation predicts.
- **The coarse grid stage needs no root-finding, including its silence filter.** For subsonic sources, heard-time is monotonic in emission-time, so the coarse delayed CPA is a closed-form/argmin minimization of slant distance over emission time (`t_heard = t_e* + d(t_e*)/c`), and the silence filter maps a heard-time window to an emission-time window by interpolating against monotonic segment-endpoint heard-times — also closed-form, not iterative. `physics/propagation.py::solve_emission_time`'s Newton iteration is reserved for fine-curve synthesis (`grid/fine.py::model_doppler_curve`), which needs emission time at arbitrary heard-times, not just at a closest approach.
- Geolocation requires real-world geospatial math (WGS84 ellipsoid, 3D slant range including terrain elevation via a DEM) — flat-earth or 2D-only distance approximations will produce wrong Doppler curves at typical aircraft altitudes/ranges.
- The two-stage coarse→fine grid search exists for performance: the coarse stage uses cheap closed-form CPA/timing filters to eliminate most of the search space before the expensive full Doppler-curve synthesis and ridge-frequency-residual scoring runs on the fine grid.
- v1 treats barometric, orthometric (DEM/MSL), and ellipsoidal heights as equivalent — a known, documented approximation, not an oversight; a geoid-undulation correction is deferred.
- `physics/propagation.py::solve_emission_time` takes plain `position_fn`/`velocity_fn` callables (time array -> ECEF array), not a `FlightTrack` object — `physics/` has no dependency on `adsb`/`types`. `FlightTrack` (added in the ADS-B ingestion stage) must expose `position_ecef(t)`/`velocity_ecef(t)` methods matching that signature, including returning NaN rows for times outside the track's sample range (callers of `solve_emission_time` rely on NaN propagating to a NaN, unconverged result rather than raising).
- Newton's method, not fixed-point iteration, is used for the propagation-delay solve — fixed-point contracts at rate `|v_r|/c` and needs too many iterations for fast aircraft; Newton uses the exact derivative `1 - v_r/c` and converges in ~4-5 iterations.
- `audio/fit.py` fits each ridge against its **own** closed-form constant-velocity-flyby Doppler model, independent of `physics/propagation.py`'s numerical solver, parametrized directly as `(f0, v, d_min, t_heard_ref)`. This is intentional duplication, not an oversight: synthesizing test audio via the numerical solver and then fitting with the independent closed form gives a real cross-check between two separately-implemented formulations. Never have one import the other.
- Synthetic test audio generators live in `tests/fixtures/`, not under `src/acoustic_geolocation/` — they are dev/test-only and are not part of the installed package (the CLI has no `synth` subcommand for this reason).
- **v1 limitation**: `audio/events.py::find_doppler_curves` takes one frequency peak per time frame (per-frame argmax), so it cannot separate two Doppler events that overlap in time with similar frequency. Time-separated or well-separated-in-frequency events are fine; true overlap would need multi-peak tracking, deferred.
- `adsb/interface.py::AdsbSource.load_tracks` returns **all** tracks in range, not just aircraft-type matches for the audio events — `grid/coarse.py`'s silence filter needs to know about every audible aircraft, including non-matching types (e.g. a jet overhead between two events is still audible and must suppress that candidate point). Narrow to matchable types afterward with `adsb/filters.py::filter_aircraft_type`, never before; `pipeline.py::geolocate` passes `all_tracks` as `silence_tracks` and only the propeller-filtered subset as `match_tracks`.
- `types.py::FlightTrack` interpolates position linearly in ECEF between samples (not lat/lon/alt) and derives velocity as the exact piecewise-constant derivative of that same interpolant, so `physics/propagation.py`'s Newton step (which assumes `velocity_fn` really is d/dt of `position_fn`) stays exact, and `grid/coarse.py`'s closed-form per-segment CPA has genuinely linear segments to work with. Queries beyond `extrapolation_margin_s` (default 60s) past either end of a track return NaN; within that margin, position/velocity extrapolate linearly from the nearest end segment. The margin exists because sound emitted near a track's last sample is often *heard* well after it (propagation delay), and `solve_emission_time`'s one-shot seed evaluates position at the heard time itself — without the margin, that seed silently dies on an in-range true answer.
- v1 requires an explicit `is_propeller` column in the local ADS-B dump rather than deriving it from a real ICAO aircraft-type-designator lookup table — that lookup is deferred.
- `grid/coarse.py::delayed_cpa` is a closed-form distance minimization over emission time per linear track segment (quadratic, clipped to the segment), vectorized across all segments with numpy, never a per-segment Python loop or `physics.propagation`'s iterative solver — that solver is reserved for `grid/fine.py`, which needs emission time at arbitrary heard-times, not just at the CPA. A per-segment Python loop here was measured at ~50s for a few-thousand-point grid; the vectorized version is ~1.5s for the same grid — "coarse" only stays cheap if this stays vectorized.
- The coarse time-offset margin and distance tolerance must account for grid quantization (a point up to `resolution/√2` from the true location) and the audio stage's own measurement error, not just a fixed constant — `grid/coarse.py::_default_time_margin_s`/`_default_distance_tolerance_m` implement this; passing a too-tight fixed `error_margin_s`/`d_min_tolerance_m` can reject the true grid cell outright.
- The silence filter checks audibility across the *entire* emission-time window implied by the two events' heard times (via `_min_distance_in_heard_window`), not just at each candidate distractor's own closest-approach instant — a distractor whose true CPA lands just outside the window can still be well within the audibility radius for part of it, and a CPA-only check misses that case (regression test: `test_silence_filter_catches_distractor_whose_cpa_lands_just_after_the_window`).
- **v1 limitation**: `delayed_cpa` returns a track's single global closest approach. An aircraft flying a repeating pattern that passes the same point more than once is only checked at its closest overall pass, not every pass.
- **Known coarse-stage ambiguity**: two non-parallel tracks can produce a near-mirror-image candidate location (both `d_min` values still roughly match, and the timing-offset shift can stay inside the coarse margin). This is expected, not a bug — resolving it is the fine-grid scoring stage's job, not the coarse filter's; coarse-stage tests bound *all* survivors to a sanity radius rather than asserting a single survivor. `tests/test_coarse_to_fine_integration.py` confirms the full pipeline actually does resolve this: fine-grid scoring picks the true point over the mirror, not just by assertion.
- `grid/fine.py` scores candidates against `DopplerEvent.curve_freqs` (the audio stage's own sub-bin ridge frequencies), **not** against resampled spectrogram brightness as the README's pseudocode describes — the ridge is already more frequency-precise than the STFT's bin width, and comparing in Hz avoids this stage needing to re-read the original audio.
- **T0 is never inherited from the coarse stage.** `grid/fine.py::score_candidate` re-seeds T0 per fine point from that point's own `delayed_cpa` timing, then refines it continuously — the coarse cell's `t0_hypothesis` is only accurate to the coarse cell's own (potentially large) position error, which doesn't carry over to a specific fine point.
- **Scalar optimization over epoch-scale absolute times is numerically broken, and will break again if repeated.** scipy's bounded Brent minimizer (`minimize_scalar(..., method="bounded")`) sizes its convergence tolerance relative to the magnitude of its argument (`sqrt(eps) * abs(x) + xatol/3`); at epoch-scale T0 values (~1.7e9), that tolerance is tens of seconds, so the minimizer accepts its very first probe as converged. Any future scalar optimization over an absolute epoch time must instead optimize over a small offset from a seed value (see `grid/fine.py::_residual_cost_delta`) and add the seed back afterward.
- `pipeline.py::geolocate` only tries the two **chronologically-earliest** detected Doppler events when more than two are found, never an arbitrary pair — they're adjacent by construction (no third detected event lies between them in time), which the silence filter's correctness depends on: pairing two non-adjacent events would let a real detected event fall inside the "nothing else was heard between these two" window and wrongly reject the true location. Trying other (or non-adjacent) event pairs is deferred.
- `cli.py`'s `--error-margin-s`/`--d-min-tolerance-m` default to `None` (auto-sized by `grid/coarse.py` from resolution and measurement error), not a fixed number — a fixed default sized for one `--coarse-resolution-m` can reject the true grid cell outright at another resolution.
- There is no `synth` CLI subcommand (see the note above on where test fixture generators live); use `acoustic-geolocate events <audio_file>` to inspect what the audio stage detects on a real recording.
- **`audio/fit.py`'s `d_min_estimate` is biased low, and its own `d_min_estimate_err` understates that bias.** On the end-to-end test's fixture, fitted `d_min` sits 60-110m below the true delayed-CPA distance, well outside 3× the fit's own reported error bar — because a finite-duration ridge only tightly constrains `v^2/d_min` near the crossing (that ratio matches truth to ~0.25%), not `v` and `d_min` independently, and `curve_fit`'s covariance doesn't know the ~75%-overlap STFT frames feeding it aren't independent samples. `grid/coarse.py`'s default `d_min_tolerance_m` (`resolution/√2`, not the 3σ term) is currently what absorbs this bias in practice — confirmed by the end-to-end test passing at both the CLI's default 200m and a looser 500m coarse resolution. Don't tighten `_default_distance_tolerance_m` without re-validating this; a real, better fix (matching `v_flight^2/d_min(point)` against `v_est^2/d_min_est` instead of comparing `d_min` in isolation) is deferred.
- **Real-world accuracy is unvalidated.** Every number in this file (sub-40m location error, sub-second T0 error, timings) comes from synthetic audio and a hand-built ADS-B dump — not a real recording or real historical ADS-B data. Treat them as evidence the pipeline's logic is internally consistent, not as expected real-world performance.
